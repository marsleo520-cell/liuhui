## 1. 问题与证据

- 用户与任务：查看生产订单的人。岗位名称未知。任务是从一条操作日志或一条接口日志的 traceId，查看这次调用的后台执行过程。
- 当前障碍：操作日志和接口日志即使有 traceId，也到不了同一次调用的执行日志。人无法把「谁改了字段」或「接口何时调用」对上具体代码路径。
- 代码事实：仓库没有正式的链路日志页面、trace 查询接口或服务列表。原型用样本日志模拟了点击后的阅读界面。
- 用户确认：操作日志增加 traceId，点击后查看后台代码逻辑。接口日志的 traceId 同样可点击，查看后台代码逻辑。用户给出的执行图是：左侧为服务名并标出 traceId，右侧为同一条 traceId 的日志；日志含请求路径、耗时、SQL 准备语句与参数，以及调用栈；同一条 traceId 会出现在业务服务和网关两侧。
- 不解决的代价：只能看到结果，看不到这次调用经过的服务和代码位置。由此造成的业务损失未知。

## 2. 目标与非目标

### 目标

1. 从操作日志或接口日志的一个 traceId 进入后，能看到参与这次调用的服务，以及按时间排列、且带同一条 traceId 的日志。
2. 日志能看出请求路径、耗时；源日志有 SQL 时能看出准备语句和参数；源日志有调用栈时能看出类名和方法名。

### 非目标

1. 不在本屏修改订单、重放请求或重新同步。
2. 不把操作日志的字段前后值再画成一张表。字段差异见《生产订单操作日志查看》。
3. 不把接口日志的筛选和详情再做一遍。见《生产订单接口日志查看》。
4. 不建设一套与这张订单无关的全站日志平台。
5. 不使用用户截图中的地址、人员、单号和报文作为正式数据。
6. 不在源日志没有调用栈时编造类名和方法名。

### 后续

1. 若确认需要，再按服务名、日志级别或关键字筛选执行记录。
2. 若确认需要，再从执行记录跳到代码仓库中的文件。

## 4. 方案说明

- 方案：执行记录是独立一屏。左侧列出这次 traceId 出现过的服务名，每个服务旁标出该 traceId。右侧按时间从早到晚列出日志行。每一行保留来源中的 traceId、时间、级别和消息。消息中若有请求路径、耗时、SQL 准备语句、参数或调用栈，按来源原文展示。
- 沿用的现有模式：无正式链路页可沿用。入口只挂在两处已确认的 traceId 上。
- 新增模式及理由：操作日志和接口日志都要进入同一种执行记录。若各做一屏，同一条 traceId 会对出两套日志。
- 被放弃的做法及理由：在日志行内用浮层只显示 traceId 文本。用户要求看到如图的执行过程，而不是只重复编号。把截图中的真实地址和人员抄进界面。那是某一次真实调用，不是规则。

## 5. 信息架构与流程

### 入口与出口

入口有两处：操作日志上的 traceId；接口日志列表或详情上的 traceId。

出口：返回打开它的那一屏。从操作日志来，回到操作日志。从接口日志来，回到日志管理，并保留筛选。Esc 与返回相同。

### 主路径

1. 用户在操作日志或接口日志点击一个 traceId。
2. 系统按该 traceId 取执行记录。
3. 系统在左侧展示本次出现过的服务名，并在每个服务上标出这一条 traceId。
4. 系统在右侧按时间从早到晚展示日志行。每一行都能看到该 traceId。
5. 用户阅读请求路径、耗时，以及来源里已有的 SQL 和调用栈。
6. 用户返回来源页。

### 分支路径

1. 该 traceId 没有任何执行记录时，系统展示「这条 traceId 没有执行记录」，并仍显示当前 traceId。
2. 正在获取时，系统展示「正在加载执行记录」。加载必须能结束，并进入成功或失败。
3. 获取失败时，系统展示「执行记录没有加载出来」。用户重试且成功后，系统展示记录，并显示「已重新获取」。
4. 用户没有查看权限时，系统不展示服务名和日志正文，只说明不能查看，并允许返回。
5. traceId 很长，或时间为 00:00:00.001、23:59:59.999，或单行消息很长时，traceId、时间和消息全文仍然可完整阅读。可以用横向滚动，不得截断到无法辨认。
6. 来源日志没有 SQL 时，不显示 SQL。来源日志没有调用栈时，不显示类名和方法名。

## 6. 功能需求

按 P0 / P1 排列。P0 是没有它任务就失败的项。

### P0-1 用 traceId 打开执行记录

- 用户故事：作为查看生产订单的人，我要从一条 traceId 打开执行记录，以便只看这一次调用。
- 规则：当用户点击操作日志或接口日志上的 traceId 时，系统只查询并展示这一条 traceId 的执行记录。
- 反馈：成功时看到执行记录或空状态。失败时看到失败说明。
- 数据：读取 traceId 及它关联的执行日志。查询接口未知。

### P0-2 看到服务和按时间排列的日志

- 用户故事：作为查看生产订单的人，我要看到哪些服务处理了这次调用、日志顺序如何，以便核对执行过程。
- 规则：当存在执行记录时，系统列出本次出现过的服务名，每个服务标出同一条 traceId。日志按时间从早到晚排列。每行包含该 traceId、时间、级别和消息。
- 反馈：成功时左右两侧使用同一个 traceId。没有记录时走空状态，不编造服务名。
- 数据：服务名、traceId、时间、级别、消息。服务名的正式清单待确认。

### P0-3 保留路径、耗时、SQL 和调用栈

- 用户故事：作为查看生产订单的人，我要看到请求路径、耗时和代码位置，以便把结果对上后台逻辑。
- 规则：当日志消息含请求路径或耗时时，系统展示路径和耗时。当消息含 SQL 准备语句或参数时，系统展示这些语句和参数。当消息含调用栈时，系统展示类名和方法名。当消息不含这些内容时，系统不补写。
- 反馈：有则可见，无则不出现假的 SQL 或假的类名。
- 数据：来源日志原文中的路径、耗时、SQL、参数、调用栈。是否脱敏待确认。

### P0-4 只读

- 用户故事：作为查看生产订单的人，我要只阅读执行记录，以便不会重放或改写这次调用。
- 规则：当用户位于执行记录时，系统不提供重放、重新同步、保存或编辑订单。
- 反馈：界面上没有这些操作。打开本屏不向业务服务发送写入请求。
- 数据：不写生产订单，不写外部系统。

### P0-5 返回来源

- 用户故事：作为查看生产订单的人，我要回到刚才的日志，以便继续核对同一条记录。
- 规则：当用户点击返回或按 Esc 时，系统回到打开执行记录之前的那一屏。从操作日志来则回到操作日志。从接口日志来则回到日志管理并保留筛选。
- 反馈：来源页的当前订单和筛选与进入前一致。
- 数据：不新增读写。

### P0-6 空、加载、失败、无权限与边界

- 用户故事：作为查看生产订单的人，我要在没有数据、加载、失败、没权限和极长内容时知道真实状态，以便不把异常当成「没有执行过」。
- 规则：当没有执行记录时，系统显示「这条 traceId 没有执行记录」，并显示当前 traceId。当加载中时，系统显示「正在加载执行记录」，并允许结束加载。当加载失败时，系统显示「执行记录没有加载出来」，并允许重试；重试成功后展示记录，并显示「已重新获取」。当无权限时，系统不展示服务名和日志正文。当 traceId 或单行消息很长，或时间为 00:00:00.001、23:59:59.999 时，系统仍能完整阅读 traceId、时间和消息。
- 反馈：见规则中的文案。
- 数据：权限判定来源待确认。失败原因码待确认。

P1：无。按关键字筛选和跳转到代码仓库放在「后续」。

## 7. 界面状态

| 状态 | 出现条件 | 用户看到 | 用户可做 |
| --- | --- | --- | --- |
| 空 | 该 traceId 没有执行记录 | 当前 traceId，以及「这条 traceId 没有执行记录」 | 返回来源 |
| 加载 | 正在获取执行记录 | 「正在加载执行记录」，没有日志行 | 结束加载。结束后进入成功或失败 |
| 成功 | 查到该 traceId 的日志 | 左侧服务名和 traceId，右侧按时间排列的日志行 | 阅读、横向滚动、返回 |
| 失败 | 获取失败 | 「执行记录没有加载出来」 | 重试、返回来源 |
| 无权限 | 当前用户不能查看执行记录 | 「当前账号不能查看执行记录」，没有日志正文 | 返回来源 |
| 边界 | traceId 或消息很长，或时间为 00:00:00.001、23:59:59.999 | traceId、时间和消息全文可完整阅读 | 滚动、返回 |

## 8. 数据与业务规则

- 对象：traceId；执行日志；参与服务。存储结构未知。
- 字段与校验：展示服务名、traceId、时间、级别、消息。消息中的请求路径、耗时、SQL、参数、调用栈仅在来源已有时展示。时间展示沿用来源日志，不另造精度。不展示用户截图里的真实地址、人员和报文。
- 权限：无查看权限时不展示日志正文。权限点名称未知。
- 排序、去重、并发、撤销：同一 traceId 的日志按时间从早到晚。同一时间的多行都保留。本屏不提供重放和撤销。
